# Задание №14. Полиморфные массивы, HashMap, RecyclerView

## Вопрос 1. Массив Animal[] с объектами Dog, Cat, Elephant

Это возможно благодаря **наследованию и полиморфизму**. `Dog`, `Cat` и `Elephant` — подклассы `Animal`, то есть каждый из них **является** `Animal`. Ячейка массива типа `Animal` хранит ссылку на `Animal`, а ссылка на объект подкласса этому типу подходит (восходящее преобразование выполняется автоматически). При вызове переопределённого метода, например `makeSound()`, выполняется версия реального класса объекта.

**Ограничение:** через ссылку типа `Animal` доступны только методы, объявленные в `Animal`. Компилятор знает лишь тип переменной, поэтому `zoo[2].trumpet()` не скомпилируется, даже если там лежит слон.

**Как обойти:** проверить реальный тип через `instanceof` и выполнить явное нисходящее приведение типа.

@code код/Demo.java ~ // Полиморфный массив ~ ((Elephant) a).trumpet();

Без проверки `instanceof` приведение объекта другого класса, например `(Elephant) dog`, вызвало бы `ClassCastException` во время выполнения.

## Вопрос 2. Принцип работы HashMap

`HashMap<K, V>` хранит пары **«ключ → значение»**. Внутри это массив «корзин». При вызове `put(key, value)` у ключа вычисляется `hashCode()`, по нему определяется номер корзины, и пара кладётся туда. При вызове `get(key)` хеш вычисляется снова: сразу находится нужная корзина, и внутри неё ключ сравнивается через `equals()`. Поэтому поиск не перебирает все элементы и в среднем выполняется за постоянное время. Ключи уникальны: `put` с существующим ключом заменяет старое значение.

```java
HashMap<String, Character> heroes = new HashMap<>();   // создание

heroes.put("Geralt", new Character("Geralt", 100));    // добавление
heroes.put("Ciri", new Character("Ciri", 80));

Character c = heroes.get("Ciri");                      // получение по ключу
```

## Вопрос 3. Преимущество ключей перед массивом и ArrayList

В массиве и `ArrayList` объект находится по **номеру**. Чтобы найти персонажа по имени, приходится перебирать весь список и сравнивать имена (время растёт с размером списка). Кроме того, индекс никак не связан со смыслом объекта и сдвигается при удалении элементов.

В `HashMap` объект находится **сразу по осмысленному ключу**: `characters.get("Geralt")`. Преимущества:
- быстрый доступ без перебора, даже при тысячах объектов;
- понятный код: ключ отражает смысл («кто», а не «какой по счёту»);
- ключ стабилен: удаление других объектов его не меняет;
- уникальность ключей автоматически исключает дубли.

## Вопрос 4. Задачи адаптера и зачем нужен свой класс

`RecyclerView` сам по себе только **контейнер**, который умеет прокручивать и переиспользовать элементы. Он не знает, **какие данные** показывать и **как выглядит** один элемент списка. Поэтому одной разметки XML недостаточно: на экране будет пустой список.

Адаптер — посредник между данными (например, `ArrayList` заметок) и `RecyclerView`:
- `onCreateViewHolder()` — создаёт View элемента из XML-разметки строки и оборачивает в `ViewHolder`;
- `onBindViewHolder()` — заполняет готовый `ViewHolder` данными конкретной позиции (текст, картинку);
- `getItemCount()` — сообщает, сколько всего элементов.

Отдельный класс-наследник `RecyclerView.Adapter` нужен потому, что эти методы **абстрактные**: библиотека задаёт только их сигнатуры, а что именно и как отображать, знает лишь наше приложение. Каждый список в приложении получает свой адаптер со своей логикой.

```java
public class NoteAdapter extends RecyclerView.Adapter<NoteAdapter.ListItemHolder> {
    private final List<Note> notes;

    public NoteAdapter(List<Note> notes) { this.notes = notes; }

    @NonNull @Override
    public ListItemHolder onCreateViewHolder(@NonNull ViewGroup parent, int viewType) {
        View item = LayoutInflater.from(parent.getContext())
                .inflate(R.layout.list_item, parent, false);
        return new ListItemHolder(item);
    }

    @Override
    public void onBindViewHolder(@NonNull ListItemHolder holder, int position) {
        holder.title.setText(notes.get(position).getTitle());
    }

    @Override
    public int getItemCount() { return notes.size(); }

    static class ListItemHolder extends RecyclerView.ViewHolder {
        final TextView title;
        ListItemHolder(View view) {
            super(view);
            title = view.findViewById(R.id.textViewTitle);
        }
    }
}
```

## Вопрос 5. ScrollView и RecyclerView

**ScrollView с динамическими TextView** создаёт View для **каждого** элемента сразу, даже для тех, что далеко за пределами экрана. При тысячах элементов это тысячи объектов в памяти, долгая начальная отрисовка и подтормаживание при прокрутке. Кроме того, при изменении данных вручную приходится пересоздавать или искать нужные TextView.

**RecyclerView и адаптер** создают View только для элементов, которые **помещаются на экране** (плюс пару в запасе), и затем их **переиспользуют**, отсюда и название. Когда строка уходит за край экрана, её `ViewHolder` не удаляется, а возвращается в пул. Адаптер в `onBindViewHolder()` подставляет в него данные новой позиции, и строка появляется с другой стороны. Количество View остаётся постоянным (около 10–15) при любом размере списка, поэтому память не растёт и прокрутка остаётся плавной. `ViewHolder` к тому же хранит найденные ссылки на виджеты, и при каждой прокрутке не нужно заново вызывать `findViewById`.
